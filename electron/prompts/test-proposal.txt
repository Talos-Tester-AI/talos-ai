**Differential Analysis (CRITICAL):**
When I provide "EXISTING FEATURES" or "EXISTING LAUNCH CONFIGS", you MUST perform a comprehensive comparison and mark status at EVERY level:

**Status Marking Rules (applies to Features, Test Cases, Steps, and Launch Configs):**
1. **NEW**: The item didn't exist before OR represents completely new functionality
2. **MODIFIED**: The item existed but has changes (e.g., a feature with new test cases, a test case with new/modified steps, a step with changed instructions)
3. **UNCHANGED**: The item exists and remains perfectly valid with no changes needed
4. **REMOVED**: The item existed before but is no longer relevant based on current codebase

**How to Perform Differential Analysis:**
- **For Features**: 
  - Mark as NEW if the feature is entirely new
  - Mark as MODIFIED if the feature exists but has any new/modified/removed test cases
  - Mark as UNCHANGED only if all its test cases are UNCHANGED
  - Include REMOVED features in the output if they no longer apply

- **For Test Cases**:
  - Mark as NEW if this test case is entirely new
  - Mark as MODIFIED if the test case exists but has any new/modified/removed steps, OR if platforms/setup/teardown changed
  - Mark as UNCHANGED only if all its steps and properties are UNCHANGED
  - Mark as REMOVED if the test case is no longer relevant

- **For Steps**:
  - Mark as NEW if this step is entirely new
  - Mark as MODIFIED if the step existed but the instruction, expectedResult, expectedFigmaNodeId, or waitTimeMs changed
  - Mark as UNCHANGED if the step is identical to the existing one
  - Mark as REMOVED if the step is no longer needed

- **For Launch Configs**:
  - Mark as NEW if this launch configuration is entirely new
  - Mark as MODIFIED if any property changed (program, args, env, etc.)
  - Mark as UNCHANGED if identical to existing
  - Mark as REMOVED if no longer applicable

**IMPORTANT**: Always include ALL items (NEW, MODIFIED, UNCHANGED, and REMOVED) in your response to provide a complete picture of what changed.
